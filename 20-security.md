## Part A — Keeping the build safe

### A1. The one rule that matters most

**Anything you paste into a chat is exposed for good.** It sits in the transcript, it gets copied into the automatic "context compaction" summaries when the conversation runs long, and it ends up in any chat archive you export later. During Assemble, several tokens and one admin password were pasted into chat and later found repeated inside compaction summaries and the raw archive (they were masked in the exported archive, but the raw transcript files still hold them).

So the standing rule is:

1. If a value **must** be pasted into chat, make it short-lived and narrowly scoped, and **rotate or delete it as soon as the job is done**.
2. Prefer putting a value into a gitignored env file yourself and telling Claude *where it is* rather than *what it is*.
3. Never ask Claude to "remind me what the password was". Keep passwords in a password manager. (Claude will answer from its memory notes if it can, and then the value is in the chat.)
4. Claude must never write a secret value into a memory note, a document, a commit message, a comment, a test fixture or a README.

> **Why:** a token pasted in chat is, by definition, compromised. Treating it that way from the start (short life, one job, rotate after) costs a minute and removes the whole class of "did that leak?" worries.

### A2. What "a token" is, and the kinds you will hand over

A **token** (or **API key**) is a long random string that acts like a password for a machine. Whoever holds it can act as you on that service. In this project Claude received, over time:

| Service | Kind of token | What it lets Claude do | Scope to ask for | Typical life |
|---|---|---|---|---|
| GitHub | Personal Access Token (PAT), fine-grained | push code, set repository secrets, edit CI files | only the project repos; Contents read/write; Actions read; **Workflows read/write** if Claude will edit `.github/workflows` | 90 days |
| Vercel | Access token | create projects, set env vars, trigger and poll deployments, move domains | the team that owns the projects | 1 day when possible (see A6) |
| Neon | CLI login (browser OAuth) plus connection strings in env files | create branches, pull env, run migrations | the one project | the OAuth login persists on the machine; connection strings live in env files |
| Google AI Studio (Gemini) | API key | AI calls from staging/local | one project with billing | rotate at cutover to the client's own key |
| Tripo (3D) | API key | 3D builds, wallet read | one account | rotate when the account changes |
| Resend | API key | send emails | "Sending access" for one domain | rotate at cutover |
| Google OAuth | client id + client secret | "Continue with Google" | one OAuth client with exact redirect URIs | rotate at cutover |
| Sentry, PostHog | DSN / public key | error reports, analytics | per app | low risk (public-ish) |
| VAPID | key pair generated locally | web push | generated by Claude with `npx web-push generate-vapid-keys` | keep with the project |

Details of *where to create* each one are in [03-services-setup.md](03-services-setup.md). This chapter is only about *handling* them.

### A3. The session token contract (paste this at the start of any session that will push or deploy)

> **For Claude — paste this:**
```
Token and secret rules for this session (they override any default behaviour):

1. Any token I paste in chat is treated as compromised. Use it for the stated job only and remind me to revoke or rotate it when the job is done.
2. Never store a token: no .git/config, no remote URL with credentials, no `git push -u` with a token URL, no memory notes, no docs, no comments, no commit messages, no test fixtures, no scratch scripts with the value hard-coded. Read tokens from environment variables or from a gitignored env file I name.
3. Before using a token, verify it with ONE cheap read-only API call (GitHub: GET /user and GET /repos/<owner>/<repo>; Vercel: GET /v6/deployments?projectId=...&limit=1). If it fails, stop and tell me; do not try other routes.
4. Push with an inline URL and never save it:
   git push https://x-access-token:<TOKEN>@github.com/<owner>/<repo>.git <branch>  2>&1 | sed -E 's/(ghp|github_pat|vcp)_[A-Za-z0-9_]+/***REDACTED***/g'
   After every push run `git config --get-regexp remote` and grep .git/config for the token; scrub if present.
5. Redact tokens, keys, database URLs and emails from any command output you show me.
6. Secrets live only in: gitignored .env.local files, Vercel project environment variables, GitHub Actions secrets. Never in tracked files. Check `git status` before every commit so a scratch file never sweeps a secret in.
7. Never run `neon env pull` for a branch whose credentials are stored as GitHub secrets (it rotates them). Ask me first.
8. Never touch the production database or the production Vercel project unless I say the word "cutover" in this session.
9. If you find a secret in a tracked file or in git history: tell me, rotate it at the provider first, then remove it from the tree. History rewriting only for a private repo where every collaborator re-clones.
10. Commit identity: <GITHUB_USER> <<ID>+<GITHUB_USER>@users.noreply.github.com> (look the numeric ID up with `gh api users/<GITHUB_USER> --jq .id`; the plain <GITHUB_USER>@users.noreply.github.com form also works on older accounts), set repo-locally. No AI attribution anywhere in client repositories (no co-author trailers, no "generated by" lines).
```

> **Why each line:** 1–3 stop a leaked token from becoming a leaked repo; 4–5 are what actually went wrong once during Assemble (`git push -u` with a token URL wrote the token into `.git/config`; it was scrubbed the same minute); 6 is why scratch scripts stay in the scratchpad; 7 is a Neon-specific trap that silently broke CI; 8 is the production boundary; 10 is the client-repo rule.

### A4. Handing over a GitHub token safely

Steps for you (low-tech):

1. GitHub → Settings → Developer settings → Personal access tokens → **Fine-grained tokens** → Generate new token.
2. Repository access: **Only select repositories** → tick the project repos.
3. Permissions: Contents **Read and write**; Actions **Read**; Workflows **Read and write** (only if Claude will edit `.github/workflows/*.yml`; without it, a push touching that folder is rejected, and Claude will route CI settings through `next.config.mjs` instead, which is a worse design).
4. Expiration: 90 days. Put the expiry date in your calendar.
5. Paste it into chat **once** with the sentence "Use this token inline only for pushes; do not store it." Or better: write it into a gitignored file such as `.env.github` (`GITHUB_PAT=...`) and tell Claude the path.
6. When the work is done, revoke it (Developer settings → the token → Delete) or let it expire.

Verification Claude runs before the first push (no output shows the token):

```bash
curl -s -o /dev/null -w "%{http_code}\n" -H "Authorization: Bearer <GITHUB_PAT>" https://api.github.com/user
curl -s -o /dev/null -w "%{http_code}\n" -H "Authorization: Bearer <GITHUB_PAT>" https://api.github.com/repos/<OWNER>/<REPO>
```

`200` and `200` means the token belongs to an account that can see the repo. A `404` on the second call means either the repo does not exist or this token's account cannot see it — GitHub deliberately does not distinguish. For the push itself use the `https://x-access-token:<GITHUB_PAT>@github.com/<OWNER>/<REPO>.git` form with `GIT_TERMINAL_PROMPT=0` set: a plain `https://<GITHUB_PAT>@github.com/...` URL made git open a credential prompt that a non-interactive session cannot answer. During Assemble three different tokens were tried on one morning before the right account's classic token worked; the check above would have said so in seconds.

**The local `gh` command line login is not a shortcut.** On this machine `gh` was logged into an unrelated account with no access to the client repos, and that never changed. Claude must not assume `gh auth status` is the identity that can push.

### A5. Commit identity and why Vercel cares

Vercel's Hobby plan refuses to build a **private** repository's commit if the commit author is not a collaborator on the Vercel project, and Hobby cannot add collaborators on private repos. The fix is to make every commit's author the GitHub account linked to Vercel:

```bash
gh api users/<GITHUB_USER> --jq .id        # the numeric account id used in the noreply address
git config user.name "<GITHUB_USER>"
git config user.email "<ID>+<GITHUB_USER>@users.noreply.github.com"
```

Set this **repo-locally, right after `git init`**, before the first commit. (Older GitHub accounts also accept the shorter `<GITHUB_USER>@users.noreply.github.com`; the `<ID>+` form is what GitHub shows under Settings → Emails and is the one Assemble used from 25 Jul 2026.) If commits already exist with the wrong author, rewrite them (`git commit --amend --reset-author --no-edit` for one commit, or `git rebase <base> --exec "git commit --amend --no-edit --reset-author"` for a branch) and force-push **with a lease**. The Assemble 3D-viewer repo and the UI repo both hit this block once each.

For the public coming-soon repo the agency identity `DeepLearnHQ-Dev <DeepLearnHQ-Dev@users.noreply.github.com>` was used because the client asked that commits "say they're from the Deep Learn HQ dev team". A noreply address links to no real profile.

### A6. Vercel tokens on a SAML team expire quietly

The Vercel team used for Assemble is protected by SAML single sign-on. Tokens issued there keep answering `GET /v2/user` with 200 while **team-scoped writes** (creating env vars, triggering deployments) start returning `403 "You must re-authenticate to this scope"`. This happened four times (August, 2 Sep, 10 Sep, 17 Sep 2026).

Rules:

- Ask for a token with a **1-day** expiry when Claude needs the dashboard for a specific job (creating projects, moving domains), and delete it after.
- Before polling deployments, Claude runs one cheap call: `GET https://api.vercel.com/v6/deployments?projectId=<PROJECT_ID>&teamId=<TEAM_ID>&limit=1` and checks the response has a `deployments` array.
- On 403, Claude stops and asks for a new token; meanwhile it verifies deployments by fetching the live URLs (`/api/version` returns the build's commit SHA).
- Claude reads the token from an environment variable (`VERCEL_TOKEN`) in scripts, never hard-codes it. Some early scratch scripts hard-coded tokens; that pattern is banned.

### A7. Env files, GitHub Actions secrets and the Neon rule

Where secrets live, and nowhere else:

| Place | What goes there | Who writes it |
|---|---|---|
| `apps/web/.env.local`, `apps/admin/.env.local` (gitignored) | everything the app needs locally: database URLs, auth secret, Google OAuth, Resend, Sentry, PostHog, Tripo, Gemini, VAPID, cron secret, admin password/session secret | Claude (from values you give) or `neon env pull` |
| `backend/.env.ci-backend` (gitignored) | the CI database branch's connection strings and storage credentials, saved **once** | Claude, once |
| Vercel → project → Settings → Environment Variables | the same values per project and per target (production / preview); staging projects get the staging branch values; **production never gets the agency Gemini key** | Claude via API, or you in the dashboard |
| GitHub → repo → Settings → Secrets and variables → Actions | `DATABASE_URL`, `AUTH_SECRET`, `ADMIN_PASSWORD`, `ADMIN_SESSION_SECRET`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_ENDPOINT_URL_S3`, `AWS_REGION` — all pointing at the **CI** database branch | Claude with `gh secret set` using the PAT |

The `.gitignore` of a client repo must contain at least: `node_modules`, `.next`, `.turbo`, `dist`, `.env`, `.env.local`, `.env.*.local`, `.env.ci-backend`, `ci-branch.env`, `.neon`, `screenshots/`, `test-results/`, `playwright-report/`, `tools/marketing/out/`, `.claude/`.

**The Neon rule.** `neon env pull --branch <name>` does not just read the branch's connection string: it **mints new object-storage credentials** for that branch, invalidating the copies stored as GitHub Actions secrets. CI then fails on every storage test with no obvious cause. Save a branch's env once (into `.env.ci-backend`), write "never re-pull for this branch" into the project's standing rules (see `templates/CLAUDE.md` §4), and if it ever must be re-pulled, update every `AWS_*` and `DATABASE_URL` secret immediately.

**When you copy a repo into a new one** (Assemble's frontend repo was copied into a fresh backend repo with a clean history on 1 Sep 2026), the new repo has **no Actions secrets**. CI failed on every commit for hours until Claude created a dedicated CI branch and set eight secrets. Do this on day one of any new repo.

### A8. Repositories, branches and what goes where

- One private repo per deliverable: coming-soon page (public, because it is a marketing page), wireframes, UI prototype, full-stack frontend, backend. Private by default for anything containing a real person's likeness (the 3D scan repo) or client business logic.
- `main` auto-deploys. Big or taste-driven changes go on a branch, get a Vercel preview, and merge only after you have verified ("since there are major changes I want you to use branching and after verified we will merge"). Tiny one-line fixes after a merge go straight to `main`.
- Experiments you reject are deleted completely, locally and remotely, so a developer never finds two versions.
- A backup repo (pushing a review branch as another repo's `main`) is fine, and a `PROJECT-HANDOFF.md` written *without any secrets* travels with the code.
- The backend repo carries **no AI attribution** at all (commits, comments, docs, tests). Earlier prototype repos had a co-author trailer; the standing rule now forbids it in any client repo.

### A9. Chat archives and memory

- Export chats through a script that **masks** `ghp_`, `github_pat_`, `vcp_`, `AIza`, `AQ.`, `sk-`, `re_`, `tsk_` tokens, Postgres URLs with passwords and any `password|secret|token|api_key = "..."` assignment, and keep the archive **outside every git repo**. Assemble's `export-history.mjs` does this (see [01-running-the-sessions.md](01-running-the-sessions.md) §9 and `templates/archive/export-history.mjs`). After exporting, grep the output for the patterns above and expect zero hits.
- Memory notes (Claude's auto-memory) may record *that* a token exists, *where* it is stored and *how to verify it*, never the value. Several Assemble memory notes were found to hold real values; the template forbids that.

## Part B — Making the app safe

This is the checklist a developer sent the user on 12 Sep 2026 ("Hide API keys, Enable RLS, Test IDOR attacks, ... Attack your own app"), and what each item became in Assemble after a 25-question round and one security push (commit `6677cba`, 13 Sep 2026). Use it as the security round for any app: each item gets a plain meaning, what to build, and the test or file that proves it.

### B1. The twenty items

| # | Item (developer's wording) | Plain meaning | What Assemble does | Proof |
|---|---|---|---|---|
| 1 | Hide API keys | keys must never reach the browser or the repo | keys only in hosting env vars; only `NEXT_PUBLIC_*` values reach the browser (analytics key, push public key, app URL) | `npm run security:secrets` on tree and history |
| 2 | Enable RLS | database row-level security (the DB itself refuses rows that are not yours) | **deliberately not used**: no browser ever talks to the DB, one server role, every query filters by the signed-in user id; documented in `SECURITY.md` with the exact commands to turn it on if a direct data path is ever added | attack suite |
| 3 | Test IDOR attacks | "insecure direct object reference": guessing another user's id in a URL | e2e spec: one account tries to read/change/delete another's items, looks, links, tickets, packing lists, 3D avatars, generation status | `tools/e2e/security.spec.ts` |
| 4 | Scan git secrets | make sure no key was ever committed | dependency-free scanner on every push (tree) and on demand (full history); any key found in history is rotated the same day | `tools/security/scan-secrets.mjs` |
| 5 | Lock admin routes | every admin API needs the admin session | every `api/admin/*` route checks the session; pages gated by middleware; a unit test fails the build if a route lacks the check; attack suite hits every admin route with every method and no cookie → 401 | `routeInventory.test.ts`, `security.spec.ts` |
| 6 | Test user isolation | users cannot see each other's data | as 3, plus other accounts' storage files → 401, shares not addressed to you unanswerable, no other account's email in any social response | `security.spec.ts` |
| 7 | Rate limit APIs | stop brute force and bill runaway | counters in the app's own database (`rate_limits` table, fixed window upsert), see B3 | `rateLimit.test.ts`, throttle e2e |
| 8 | Lock storage buckets | private files only through the server | private bucket, served through `/api/storage/[...key]` after a session check matching the owner prefix `u<id>/`; shop and advert images under `public/` on purpose | four e2e cases |
| 9 | Validate all inputs | refuse malformed requests | one strict zod schema per writing route (POST/PATCH/PUT/DELETE): unknown fields dropped, types/lengths/enums enforced, plain-sentence 400 | `validate.test.ts` |
| 10 | Block unauthenticated routes | everything needs a session unless listed | a short public allow-list with a "why" per entry; a unit test walks every `route.ts` and fails if one lacks `getCurrentUser(`, `isAdmin(` or `cronAuthorized(`; the attack suite knocks on every route signed out (found three real gaps the first time) | `routeInventory.test.ts` |
| 11 | Test SQL injection | text fields cannot run SQL | parameterised tagged templates only; a unit test fails on `sql.raw` or string-built SQL outside an exact allow-list; classic payloads pushed through every text field are stored as text | `sqlScan.test.ts`, `security.spec.ts` |
| 12 | Remove sensitive logs | logs must not hold emails, tokens, photos | `lib/log.ts` scrubs emails, bearer tokens, provider key shapes, 32+ character secret-shaped runs, and blanks fields named password/code/token/secret/authorization/cookie; Sentry with `sendDefaultPii: false` and the same scrubber | `log.test.ts` |
| 13 | Block field tampering | a request cannot set money or status | plan, credits, `emailVerified`, `suspended`, free-detection counters, ownership ids, share tokens are never settable from a request; the owner is always the session | attack suite ×4 |
| 14 | Restrict file uploads | only real images, no hidden metadata | bytes decoded with `sharp` (jpeg/png/webp/heif), re-encoded (orientation baked, EXIF/GPS/XMP/ICC dropped, HEIC → JPEG); a text file renamed `.jpg` is refused; no size cap beyond the body limit (client's choice) | `uploads.test.ts`, GPS-strip e2e |
| 15 | Secure server logic | the browser sends intent, never amounts | prices, credit costs, allowances, AI spend and ownership computed on the server; price changes need the owner's emailed code and are audited | admin-money e2e |
| 16 | Trim API responses | return only what the screen needs | names/usernames only for other people; no hashes, codes, tokens, storage keys, raw AI output or prompts, stack traces or DB error text | live checks |
| 17 | Secure auth sessions | a stolen cookie can be revoked | admin sessions server-side (7 days, "Log out everywhere", 2FA code burned after five wrong guesses); user password change or account delete bumps `session_version` so every other device signs out; cookies server-only and same-site | `adminSession`, `suspended.test.ts` |
| 18 | Scan dependencies | known-vulnerable packages fail the build | `npm run security:audit` in CI (high/critical fail unless a documented **expiring** exception); Dependabot alerts, automated security fixes, weekly grouped PRs | `tools/security/audit.mjs` |
| 19 | Test record access | covered by 3, 6, 10, 11 | — | as above |
| 20 | Attack your own app | run the attacks on every push | `security.spec.ts` runs in CI; an external penetration test is a post-launch item | CI |

Plus three one-line browser headers (`X-Frame-Options: DENY`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy: camera=(self), microphone=(), geolocation=()`), an Origin check on every state-changing call (403 "Blocked cross-site request." when the `Origin` host differs from the request host; requests with no Origin, such as the scheduler, pass), and constant-time comparison of the cron secret.

**Deliberately deferred** (agreed in the round, written into `SECURITY.md`): Content-Security-Policy (needs an audit of inline styles, the 3D viewer and the camera first), an external penetration test after launch, Vercel firewall rules at cutover, RLS (see item 2).

### B2. Authentication, in plain words

- **Users:** Auth.js v5 with Google OAuth and email + password. Email sign-up sends a 6-digit code (stored as a SHA-256 hash, 10-minute expiry, one live code per email and purpose, five wrong guesses drop it). Passwords are bcrypt-hashed with strength rules (8+ characters with a number). "Forgot password" never reveals whether an email exists. Sign-in over the rate limit returns the same answer as a wrong password so the throttle reveals nothing.
- **One sign-in method per email** (batch 3, 17 Sep 2026): a Google account trying email sign-up is stopped *before any code is sent* and told "This email signs in with Google"; a password account tapping Google is sent back to email login. This closed a real hole where a Google sign-in could mark someone else's unconfirmed password account as verified. The refusal reason travels in a 5-minute cookie, never in the URL.
- **Suspension is enforced on the server:** every request from a suspended account gets `403 { code: "suspended" }`, the app signs out and shows a modal with the support email, and every way back in (password, Google, code, reset, sign-up with that email) shows the same modal. Suspending in admin bumps the session version so open sessions end at once.
- **Admin:** separate from user auth. Password checked against a scrypt hash stored in an `admin_settings` row (env `ADMIN_PASSWORD` only as a fallback while no hash exists) → emailed 6-digit 2FA code → a **server-side session row** (revocable, "Log out everywhere"). 2FA recipients are `ADMIN_EMAIL` plus an optional comma-separated `ADMIN_EMAIL_CC` (only for the sign-in code, not other alerts).
- **Save lock on anything that changes what users pay or get** (16 Sep 2026): credit prices and caps, plans, packs, AI models, budget bands, provider prices. Saving asks for a fresh code emailed **only to the owner address**, valid 10 minutes; a correct code unlocks that admin session for 15 minutes; five wrong guesses lock saving for an hour; the route answers `423 { needsOtp: true }` when locked; every change is audited (who, when, old, new) and raises an admin notification. A request carrying the raw `ADMIN_SESSION_SECRET` (the emergency key that tests use) is still allowed to save but is audited as "environment key" and raises an "Emergency key used" alert.
- **Admin alerts never reach a customer account.** They live in their own `admin_notifications` table (this was a real bug: the admin's personal user account was receiving AI budget alerts in the customer app).

### B3. The rate-limit table (copy and adjust)

Stored in the app's own database so it behaves identically on local, CI, staging and production, with no extra service. One upsert per hit: `insert ... on conflict (key) do update set count = case when lapsed then 1 else count + 1 end ... returning count, minutes_left`. Key is `<kind>:<subject>` lowercased; client IP from the first `x-forwarded-for` hop, then `x-real-ip`. Over the limit every route answers `429 "Too many attempts — try again in N minutes."`

| Kind | Subject | Limit |
|---|---|---|
| `signin-email` | email | 10 per 15 min |
| `signin-ip` | IP | 10 per 15 min |
| `signup` | IP | 5 per 60 min |
| `verify`, `resend`, `reset` | email | 5 per 15 min |
| `forgot` | email | 5 per 60 min |
| `ai` (match, detect, render, avatar checks) | account | 200 per day (the shared demo profile gets 2,000 so a presentation never trips it) |
| `upload` | account | 300 per day |
| `public-ip` (public share page votes/comments) | IP | 60 per hour |
| `public-device` | device id | 20 per hour |
| admin sign-in and 2FA | email / IP | 5 guesses, then lockout |

The e2e global setup clears test-pattern counters (`%test.local%`, TEST-NET `203.0.113.*`, test device ids) so back-to-back runs never start locked out.

### B4. Uploads and storage

- Every upload passes `normaliseUpload`: decode with `sharp`, accept only jpeg/png/webp/heif, re-encode so orientation is baked and all EXIF/GPS/XMP/ICC metadata is gone. This is both a safety check (a script renamed `.jpg` is refused) and a privacy one (a shared photo never reveals where it was taken).
- Storage is one private bucket per environment (Neon Object Storage, S3-compatible, `forcePathStyle: true`), keys `u{userId}/{kind}/{uuid}.{ext}`; public catalogue images under `public/`. All private reads go through `/api/storage/[...key]`, which checks the session and that the key starts with the caller's own prefix; a live check confirmed someone else's key is refused.
- **Never overwrite an object key.** The proxy sends immutable cache headers; rotated avatars written to the same key stayed sideways for users until new keys were used.
- **Account deletion removes every object under `u<id>/`** first, then rows. Failures go into a `storage_cleanups` queue with an admin retry card; deletion of the account never blocks on a storage error. The demo profile (id 1) is refused in both the route and the helper. Files of deleted accounts return 404 to everyone.

### B5. Scans and gates that run on every push

```bash
npm run security:secrets     # node tools/security/scan-secrets.mjs --tree   (exit 1 on a hit; output masked)
node tools/security/scan-secrets.mjs --history        # every commit on every branch
npm run security:audit       # node tools/security/audit.mjs                 (npm audit gate, high/critical)
npx vitest run               # includes routeInventory, sqlScan, log scrubber, copy audit, locked-key list
E2E_DB=1 npx playwright test tools/e2e/security.spec.ts --project=mobile   # the attack suite alone
```

Scanner patterns worth copying: Google `AIza...`, Stripe `sk_live/sk_test`, Resend `re_`, GitHub `ghp_`, Vercel `vcp_`, AWS `AKIA`, Tripo `tsk_`, Postgres URL with password, private key blocks, JWTs, and a generic `secret|token|password|api_key = "..."` with a placeholder allow-list (`changeme`, `your-`, `<...>`, `example`, `${`, `process.env`, the public demo sentinel). Tree mode uses `git ls-files --cached --others --exclude-standard` so gitignored `.env.local` files are never read; test files are only checked for the specific key shapes (they carry fixture passwords by design).

Audit-gate exception format: package, exact node paths, advisory ids, a reason it cannot be reached, and a `reviewBy` date; **once the date passes the gate fails on purpose** so the list cannot quietly become permanent. Assemble carries one: `postcss` nested inside Next.js, build-time only, review by 1 Dec 2026, because the fix needs a major Next.js upgrade that was refused days before launch.

## Part C — Privacy and consent by design

These decisions were product decisions, made in question rounds, but they are security work too. Carry them into any app that handles photos of people.

- **Consent is specific, in context and recorded.** Assemble records AI-photo-analysis consent and photo-ownership attestation ("The photos are of me, or I have the person's consent") with timestamps; detection, renders and 3D builds refuse with `403 { consent }` when missing. Consent for 3D processing is asked once, on first use, and is revocable in Settings (re-prompt after revoke). Claude argued for just-in-time consent over an onboarding checkbox because it is legally stronger and clearer; the user agreed.
- **Faces, bodies and skin tone may count as biometric or special-category data** (GDPR, BIPA). Say so in plain words in the consent copy, keep the data minimal, and make deletion real.
- **Data minimisation:** in September the onboarding was trimmed and sizes, body measurements, body type, skin tone and fit preference were removed from collection *and deleted from stored profiles and the data export* (migration 016), with the privacy policy, consent screens and the landing page's privacy section updated in the same push.
- **Admin never sees user photos.** The admin user-detail page shows names and counts only, matching the privacy policy wording.
- **Account deletion is immediate and complete**: rows in every table, storage objects, share copies, profile pictures, support attachments. The copy says so ("deleted immediately and cannot be recovered"); the earlier "within 30 days" wording was a false promise and a unit test now bans such phrases.
- **Public share links** use unguessable 22-character tokens, are created explicitly, are revocable, and re-enabling issues a fresh code; the dead-link page is identical for revoked and never-existing codes (no enumeration). The page shows first name and picture only; no username (strangers could look the person up), no closet photos, no email, no prices; receivers never see "pieces to buy". One vote per device, per-device comment rate limit, links and over-long text refused, a report flow to admin.
- **Photo checks protect people too:** closet photos with a face or a mirror selfie are refused (faces are kept out of closet AI calls); avatar photos must show exactly one person; refused photos are never stored and never charged.
- **Vendor names stay out of the UI** ("the 3D engine", never the provider's brand) because the app is not sponsored.
- **Marketing personas are AI-generated fictional people**, never presented as customers or as real, with one plain footer line saying so; no fake testimonials; provider watermarks left intact. The client's own likeness is never used on public pages without a separate decision.
- **Emails are limited** to sign-in codes and support tickets ("nothing else"), which protects sender reputation and reduces what the app can leak.

## Part D — Environment separation

The single most valuable habit from Assemble. One mistake in August (a CI run reset the demo profile while a real paid 3D build was polling the same production database) turned into a rule.

```
Neon project
├── production   ← only the live app; migrations only at cutover, after a fork rehearsal
├── staging      ← backend development, presentations, local e2e runs (E2E_DB=1)
├── ci-backend   ← GitHub Actions for the backend repo (own database AND own bucket)
├── ci           ← GitHub Actions for the frozen frontend repo
└── cutover-rehearsal (temporary fork of production; deleted after the rehearsal)
```

Rules:

1. **Never share a database between CI and any live environment.**
2. Every migration runs on staging **and** the CI branch the same day (a CI branch created before migration 003 failed weeks later on a missing column).
3. Migrations are additive and re-runnable (`IF NOT EXISTS`, count-guarded seeds). A migration that changes what a still-deployed build reads (Assemble's 005 moved Google photo URLs between columns) runs **only at cutover**.
4. Before cutover: fork production, run every migration plus the config and verify scripts on the fork, fix what fails, delete the fork. Then create a `pre-cutover-backup` branch as a restore point. See [15-payments-and-cutover.md](15-payments-and-cutover.md).
5. The agency's paid AI key goes on local and staging only. Production waits for the client's own key ([Part E](#part-e--handing-keys-over-from-the-client)).
6. Tests never call real paid engines (`GEMINI_MOCK=1`, `TRIPO_MOCK=1` on **every** test server; the admin server once lacked the flag and product tests called the real model).
7. Nothing changes in the production repo or domain "until I say cutover". Urgent production fixes go to the frozen frontend repo first, then are mirrored to the backend repo so they are not lost.
8. **Deleting live data is a three-step act**: a read-only query first, the exact matching rows shown to you, and a fresh explicit "run it" from you before anything is deleted (the Claude Code desktop app blocks a destructive command on live data until you choose to proceed — that block is a feature; on 10 Sep 2026 it stopped a production user deletion until you had seen the four matches). The script deletes rows **and** the accounts' storage objects, then lists what remains.

## Part E — Handing keys over from the client

At cutover the accounts that **bill or represent the business** must be in the client's name (domain, Google Cloud project with billing and the Gemini key, the 3D engine account, email sending, Google sign-in client, admin login, later app stores and payments), while code, CI, hosting, database and monitoring stay with the agency. Assemble's `CLIENT-HANDOVER-CHECKLIST.md` (13 Sep 2026) is the template; the security-relevant part is **how the keys travel**:

1. Ask the client to use **Bitwarden Send** (a text Send, expire after one day and one opening, optional password given by phone), or to read a key out by phone.
2. Never chat, email, SMS, WhatsApp or a shared document; those keep copies forever.
3. Confirm receipt; the client can rotate at any time and the agency swaps the key within the hour.
4. Keys go straight into Vercel env vars and the local `.env.local`, then a redeploy; nothing else records them.

## Part F — The security question round (reusable)

The 25 questions Claude asked on 12–13 Sep 2026, condensed into the decisions to take for any app. Use them with the kickoff block in B5.

1. Status per item with evidence first, then fix real gaps in one push? (Recommended: yes.)
2. Attack tests kept as e2e that run on every push, or a one-off? (Every push.)
3. RLS or server-side checks? (Server checks when no browser reaches the DB; document why.)
4. Where do rate limits live? (Own database; no new service; identical everywhere.)
5. Which routes get limits? (Sign-in/up/codes/reset; AI calls; uploads; public votes/comments; admin sign-in and 2FA.)
6. Full git-history secret scan now plus a scanner on every push? (Yes; GitHub's own scanning is paid on private repos.)
7. Policy when a key is found in history? (Rotate the same day; record it.)
8. `npm audit` gate plus Dependabot? (Both.)
9. Will Claude edit CI files? (Then the PAT needs the workflow scope.)
10. Admin sessions: server-side with "Log out everywhere" and a 2FA guess limit? (Yes.)
11. User sessions: sign out other devices on password change or delete? (Session version.)
12. Private files only through the server after sign-in; catalogue public? (Yes, with a test.)
13. Uploads: content sniff and metadata strip; size cap? (Sniff and strip; the cap is a product choice.)
14. One strict schema per writing route? (Yes.)
15. Which fields must never be settable from a request? (plan, credits, verified, suspended, owner ids, tokens.)
16. What to trim from responses? (Other users' emails/ids, hashes, codes, tokens, storage keys, raw AI output, stack traces.)
17. Logging policy and Sentry PII? (Scrub; PII off; unit test.)
18–19. Demo account in production: keep, guard, or remove? (Product choice; Assemble kept it behind a hidden address with nightly resets.)
20. Cron routes: secret always, constant-time compare, test? (Yes.)
21. Origin check on state-changing calls? (Yes; cheaper than CSRF tokens.)
22. Headers: which, and CSP now or later? (Three one-liners; CSP later.)
23. SQL: scan for string-built queries plus payload tests? (Both.)
24. Documents? (`SECURITY.md` mapped to the requester's list; a one-page plain summary.)
25. One push or several? (One: one migration, one review, one CI run, one phone retest.)

## Assemble example (what actually happened, with dates)

- **9 Jul 2026** — first push denied (403): the local `gh` account had no access; a classic PAT pasted in chat worked; Claude warned to revoke it. The pattern (inline URL, redact output, remind to rotate) started here and never changed.
- **22 Jul** — the July PAT had been revoked as advised; push failed with "Invalid username or token"; a fresh one was issued. Same day, a 3D-viewer push showed the token had been used with `git push -u` and had landed in `.git/config`; scrubbed within a minute; "never `-u`" became a rule.
- **25 Jul** — Vercel blocked a private-repo deploy because the commit author was the machine's global personal identity; fixed with a repo-local noreply identity and a force-push with a lease. Happened again on 5 Aug for the UI repo.
- **5 Aug** — three GitHub tokens tried in one morning (wrong account, fine-grained without repo access, classic that worked). Claude checked `/user` and the repo list each time.
- **28 Aug** — Vercel token (1-day expiry recommended) used to create three projects and move domains; PAT lacked the `workflow` scope so the CI file could not be pushed until you added it; Google OAuth, Resend, PostHog, Sentry keys pasted in chat and stored in env only. Late that day a CI run reset the production demo mid-3D-build → dedicated Neon `ci` branch.
- **1 Sep** — backend repo created with a clean single-commit history and no AI attribution; CI failed on every commit until eight Actions secrets and a `ci-backend` branch existed; the admin password was asked for and answered in chat (lesson: password manager).
- **2 Sep** — the profile screen was found to fall back to the browser's Google session while loading, leaking your email onto the demo view; identity now comes only from the server.
- **10 Sep** — GitHub PAT expired (401) and was replaced with a fine-grained one; Vercel token expired again; both memory notes now say "check with one call before relying on it".
- **12–13 Sep** — the 20-point security round: 25 questions, three parallel workstreams, a fix-until-clean loop that found three routes answering signed-out (ad tracking, friends list, product feedback), a critical Next.js advisory and a drizzle-orm SQL-injection advisory fixed, 200 e2e green, 19 live checks, `SECURITY.md` and `SECURITY-SUMMARY.md` shipped as `6677cba`. Result: 16 of 20 items in place or added, 1 not applicable by design (RLS), 3 deferred by your decision.
- **13 Sep** — `CLIENT-HANDOVER-CHECKLIST.md` with the Bitwarden Send rule; demo profile renamed to "Demo User" with a reserved `example.com` address so it can never receive mail.
- **16–17 Sep** — admin save lock with OTP and audit trail; one sign-in method per email; server-enforced suspension; a `sql.raw` in a new admin route was caught by the scan gate before commit.

## Pitfalls (symptom → cause → fix)

| Symptom | Cause | Fix / prevention |
|---|---|---|
| Token appears in `.git/config` | `git push -u` with a token URL | never `-u` with a token URL; grep config after every push |
| "Repository not found" on push | token belongs to another account (GitHub hides "no access" as 404) | check `/user` and the repo with the token first |
| Vercel API 403 "re-authenticate to this scope" while `/v2/user` still works | SAML team token expired | one cheap check call first; new token; verify via live URLs meanwhile |
| CI storage tests fail after `neon env pull` | pulling env rotated the branch's storage credentials | save branch creds once; never re-pull; update all secrets if you must |
| CI red on every commit of a brand-new repo | no Actions secrets came with the copied code | set secrets and a CI DB branch on day one |
| Real paid build failed mid-poll | CI reset the demo on the same production database | dedicated CI branch (DB and bucket); never share |
| Admin alerts in the customer app | alerts were in-app notifications to the admin's user account | separate admin notifications table |
| Demo screen showed your email | UI fell back to the browser's Google session while loading | identity from the server only |
| Product tests called the real AI model | mock flag set for the web server only | mock env on every test server; a "no real provider calls in tests" guard |
| Push rejected when touching `.github/workflows` | PAT without the workflow scope | request Contents + Workflows up front |
| Secret found in a memory note or scratch script | value written instead of a location | rule: never store values; read from env |
| Google `redirect_uri_mismatch` on staging | OAuth client lists only the production callback | register staging callbacks when creating staging projects |
| Delete "did not work" for the user | confirm word was case-sensitive; feedback was a small toast | case-insensitive word, inline state, server reason shown; e2e on a throwaway account |
| Rotated files still served old | immutable cache + overwritten key | never overwrite an object key |
| Play Protect flags the install on Samsung Internet | Samsung's WebAPK packaging, not your manifest | route Samsung users to Chrome; only a store listing removes the warning |
