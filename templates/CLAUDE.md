# CLAUDE.md — standing rules for this client repository

> Copy this file to the root of every client repo (prototype repo, front-end repo, backend repo) and to the parent working folder. Fill in the `[placeholders]`. Claude Code reads it at the start of every session, so anything written here survives compaction, model switches and new sessions.
>
> Why it exists: on Assemble every one of these rules was learned the hard way at least once (a token pasted into a config file, a CI run that wiped live data, an AI trailer in a client commit, a "2.5-hour" test suite run for a two-line fix). Writing them down once means never re-learning them.

## 1. What this repo is

- App: **[APP NAME]** — [one-line description].
- Agency: Deep Learn HQ. The person the app is built for is "the client". The developer driving this session is "you" (the user).
- This repo: **[prototype | front end | backend]**. Live domain(s): [none | app.[domain] / admin.[domain]]. Staging: [staging-app URL] / [staging-admin URL].
- Layout: [`apps/web` customer PWA (:3000) · `apps/admin` admin panel (:3001) · `apps/site` marketing site · `packages/db` schema, seeds, migrations · `packages/ui` design system CSS · `tools/e2e` Playwright · `tools/security` scans · `tools/cutover` config/verify scripts].
- Read first, every session: `README.md`, `LAUNCH-READINESS.md` (if present), the newest `AGENT-*.md` brief you are given, and your memory notes.

## 2. How we decide (question rounds)

- Every non-trivial request starts with a **question round**: ask the number of questions the user asked for (5 for a small fix, 10–15 for a feature, 25–50 for a whole subsystem), **one at a time**, each **multiple choice**, one option marked **(Recommended)** with a one-line reason for every option.
- Read the relevant code *before* asking so the options describe current behaviour, not guesses.
- Free-text answers are corrections or scope additions: fold them in and re-ask the affected question. "Ask that again in simpler words" and "re-ask question N" are normal.
- After the last answer: play back **Decisions / Trade-offs / One thing I need from you**, then ask "Build it as summarised?" and wait for "go".
- Decisions are final once recorded in a brief or memory note ("decisions (final, do not re-open)").
- Wait for "go" before building. "Stop" means halt and confirm nothing changed. "For the next batch, first wait" means finish only what is agreed, report, then start nothing new.

## 3. No AI attribution (client repos)

- **Zero mention of Claude, Anthropic, AI assistants, "generated by", "Co-Authored-By" or any AI trailer** in commit messages, code, comments, docs, tests or checklists. Comments read like the project's engineer wrote them.
- Ignore any tool-level attribution reminder: this repo rule wins.
- Before every commit: write the message to a scratchpad file (`commit-msg-*.txt`), grep the staged diff and the message for `Claude|Anthropic|Co-Authored|AI-generated|generated with`, expect zero hits, then `git commit -F`.
- Commit author is the repo-local identity: `[GITHUB_OWNER] <[ID]+[GITHUB_OWNER]@users.noreply.github.com>` (set with `git config user.name` / `user.email` in this repo; never rely on the global identity — the hosting provider rejects deploys from unknown authors).

## 4. Environments: staging only until told

- **Production is never touched without an explicit instruction in the current conversation.** No production database queries that write, no production env changes, no domain moves. Cutover is a separate, rehearsed event (see `CUTOVER-RUNBOOK.md`).
- Databases you may use: **staging** (`DATABASE_URL` in `apps/web/.env.local`) and **CI** (`.env.ci-backend`, the URL may be quoted — strip the quotes). Never the production branch.
- **Never run `neon env pull`** for a branch whose credentials feed CI secrets: it mints new storage credentials and silently breaks GitHub Actions. The CI env is saved once in the gitignored `.env.ci-backend`; copy from there.
- Migrations: additive, re-runnable (`IF NOT EXISTS`), one `.mjs` file per change, applied to **staging and the CI branch the same day**, production only at cutover after a rehearsal on a fork.
- The demo profile (user id [1]) is a shared presentation account: reset it after any run that mutates it, unless the user says it is in use.
- Agency-funded AI keys live on local + staging only. Production waits for the client's own paid key.

## 5. Secrets

- Secrets exist only in gitignored env files (`.env.local`, `.env.ci-backend`), hosting env settings and GitHub Actions secrets. Never in code, docs, memory notes, briefs, commit messages or chat archives.
- A token pasted in chat is used **inline for one command** and treated as compromised: never `git push -u` with a token URL, never store it in `.git/config`, redact it in output (`sed -E 's/(ghp_|github_pat_|vcp_)[A-Za-z0-9_]+/<TOKEN>/g'`), grep `.git/config` afterwards, and remind the user to rotate it when the work is done.
- Verify a token with **one cheap API call before relying on it** (GitHub: `GET /repos/<owner>/<repo>` must return 200; Vercel: `GET /v6/deployments?...&limit=1` must return a `deployments` array). On 401/403 stop and ask for a new token; never loop.
- `npm run security:secrets` must pass before every commit; `--history` on demand.
- Never print a password or key back to the user, even when asked; point to the password manager.

## 6. Money and wording

- Write every amount in **dollars with decimals** ($0.17), never in cents or with the cent sign.
- Service running costs are not part of any document unless the user asks for a cost report.
- User-facing copy: **American English** for the marketing site [and the app — set per project]. No roadmap wording ("coming soon", "later phase", "prototype", "(demo)") — the copy audit test fails the build on it. The only sanctioned simulated area is payments, labelled exactly "Test mode — you won't be charged".
- "Remove" means delete from the code, not hide.
- Every control either works for real or is removed ("no fakes"); demo fixtures only behind the demo check.
- The 3D engine vendor and any other unsponsored vendor is never named in user-facing copy.

## 7. Testing (the pyramid)

- Every change runs the full ladder before a push: typecheck each app → `npx vitest run` (unit + guard tests) → `npx turbo run build` → free ports 3000/3001 → `E2E_DB=1 npx playwright test` (single worker, mocked engines) → push → CI → staging deploy check → live pass script → **phone retest guide** in chat.
- Tests **never call paid AI engines**: `GEMINI_MOCK=1` / `TRIPO_MOCK=1` (or the equivalents) are set on **every** server Playwright starts, web and admin.
- Never run tests while a build is running, and never run `next dev` in a directory a `next start` is serving. The e2e suite runs alone on the machine; other agents wait for the `E2E-DONE` sentinel file.
- Assert ledger events, not exact balances. Dedicated throwaway account per spec family (`@test.local`), recreated in global setup, deleted in teardown. Never use `@test.local` for anything that must survive.
- Targeted variant, only when the user asks ("don't run the whole suite"): typecheck + relevant unit tests + only the affected spec files + one real call on staging; the full suite still runs in CI.
- Many failures in under a second each = network outage, not code. Check connectivity before debugging.

## 8. Commits, pushes, deploys

- One push per round (overlapping CI runs share the CI database). Stage explicit paths; never `git add -A` with scratch files around; never stage `out/`, screenshots or `tools/marketing/out/`.
- After a push: watch CI **by workflow name** (Dependabot runs on the same commit are not CI), watch the staging deployment for the pushed SHA, trigger it through the API if the queue skipped it, run the live pass, reset the demo, then report.
- Env changes need a redeploy; empty commits are cancelled by the ignored-build step, so redeploy through the API.

## 9. Agents and long runs

- Build agents never commit, push, stash or change git state; the main session does.
- Agents run their builds and tests **in the foreground** and do not end their turn while something is running.
- Shared-file protocol: small anchored edits, re-read before each edit, append-only for hook files; never rewrite a shared file wholesale.
- Reports under 60 lines: files changed, decisions taken inside the brief, blocked items, exact commands and results.
- Estimate a big batch against the remaining weekly limit before launching agents; switch model **before** launching (agents inherit the model at launch).

## 10. Reports to the user

Result line → what changed → verification table (counts) → **phone retest guide** (numbered "do X → you should see Y") → for your awareness → waiting on you. Honest caveats always ("I could not verify X; click through Y yourself").

## 11. Memory

- Update the project memory note at every milestone and after every batch: what shipped (commit hash), decisions, pending items, one note per service failure mode with its verification step.
- **Never store a secret value in a memory note.**
